2. FEATURES BUILT FOR MY PART
============================

A. AI ORCHESTRATOR AGENT
The agent observes the current donation/workflow state, asks the configured
AI model for a structured plan, validates that plan, executes an allowed action,
and observes the result before planning subsequent work.

The supported actions are:
- Prepare recipient candidates through the matching integration.
- Request recipient ranking after eligibility evaluation.
- Coordinate pickup after recipient acceptance.
- Retry an eligible failed stage within its remaining retry budget.
- Request a fresh eligibility/matching round.
- Wait briefly when enough safe time remains.
- Escalate a blocked workflow to an operator.

The model's choice controls what happens; it is not just an explanation added
to a fixed dispatcher. The model cannot run arbitrary code, select arbitrary
worker names, approve unsafe food, reserve food directly, change capacity,
extend deadlines, or override transaction/version checks.

Each plan saves a decision audit: provider/model, input facts, selected action,
short operational explanation, execution outcome, and fallback/rejection reason.
The model receives sanitized workflow facts, not addresses, contact details,
donor free text, or API keys.

The shared app-wide AI configuration now detects your saved Gemini key and
resolves to gemini-2.5-flash. This is configuration verification only; a live
Gemini request has not yet been verified.

Decision modes are deliberately different:
- model: a real configured model supplied an accepted plan.
- rules: the explicit deterministic baseline was used.
- fallback: a provider/network failure caused safe baseline behavior.
- rejected: an invalid model plan was rejected and escalated.

B. DURABLE DISPATCH, RETRIES, AND RE-MATCHING
Workflow steps, events, receipts, and outcomes are persisted in PostgreSQL.
An outbox records work before publication to Redis/Celery. Separate queues
handle intake, orchestration, matching, and reservation work.

Version checks, matching rounds, leases, and dispatch tokens prevent outdated
workers or duplicate messages from applying an extra business effect.
Retries are bounded; persistent failures are saved for operator inspection
and audited replay. Declines or changed eligibility can request another round.
Previously declined/released recipients are excluded where applicable.

Deadlines and recovery are checked independently of model availability.
Expired or terminal donations cannot be reopened by an AI plan or replay.
Food already collected cannot be offered to another recipient.

C. RESERVATION AND DOUBLE-BOOKING PREVENTION
Recipient acceptance atomically creates the reservation, allocates capacity,
updates donation status/history, and records the resulting event/response.

Optimistic version checks reject stale commands. Database locks and uniqueness
constraints protect active reservations, assignments, and shared capacity.
Two requests cannot legitimately reserve the same donation twice or allocate
more receiving capacity than is available.

Repeated requests using the same idempotency key and body return the saved
response. Reusing that key with a different body is rejected.
Pre-collection release/cancellation returns held capacity once.

D. DRIVER ASSIGNMENT, PICKUP, AND DELIVERY
The backend supports driver assignment, acceptance, decline, pickup, and delivery.
Only the assigned driver can perform the relevant commands. Overlapping driver
commitments are checked. Driver decline can request another feasible driver;
absence of one can release the hold and request re-matching.

Pickup requires explicit handling confirmation and the observed quantity.
Timing, route freshness, and eligibility are rechecked before collection.
Delivery requires confirmation and a current receiving window.

Delivery completes the reservation, records impact once, and updates capacity
accounting. Duplicate delivery must not count food or impact twice.

The reservation/pickup agent executes transactional business rules. The new
model-driven decision loop is specifically in the Orchestrator Agent.

E. NOTIFICATIONS AND LIVE STATUS
Notification jobs have stable effect IDs, retry limits, and persisted receipts.
The implemented sandbox adapter records local notification delivery evidence.
Real email/SMS delivery still requires a provider adapter and configuration.

Backend SSE endpoints publish authorized committed events and support reconnect
and replay with Last-Event-ID. This supplies the backend for live UI updates;
Mithil's full screen integration is a separate deliverable.

F. AUTHORIZATION, OPERATIONS, AND CONTRACTS
Backend routes enforce verified identity, membership, role, and resource scope.
Local demo identities require explicit local demo settings.
Operators can inspect failures, request audited replay, view status/impact,
and read orchestrator decisions. JSON Schema, TypeScript, and OpenAPI contracts
were updated for client integration.
