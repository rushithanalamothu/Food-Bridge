# Intake v0.3 implementation alignment

This reconciles the [original individual specification](donation-intake-eligibility-v0.3.pdf) with the shared project design. The PDF remains unchanged. The project owner requested preservation of the existing safety boundaries while implementing intake-owned gaps. This record describes implemented behavior and explicit amendments; it does not certify the entire donation-to-matching pipeline complete.

## Integration decisions

1. **Donor confirmation remains mandatory.** `POST /donation-drafts` produces a reviewable proposal; `POST /donations` accepts confirmed structured data and returns 202 after commit. Extraction is synchronous and bounded in this slice (ADR-012), rather than being silently advertised as a queued Orchestrator operation. Model failure produces a reviewable basic proposal, never a successful safety approval. Shared gateway login/provisioning and general dispatch remain their owners' work.
2. **One lifecycle vocabulary.** Keep the shared donation states (`submitted`, `matching`, etc.). A confirmed submission is not already a matched or reserved donation. `EligibilityResult.donation_decision` separately reports `eligible`, `rejected` or `needs_review`, with `donation_reasons`; per-candidate decisions retain established reason codes. This replaces the PDF's separate aggregate `ELIGIBLE`/`REJECTED` lifecycle vocabulary without creating another state machine or renaming other owners' contracts.
3. **Evidence instead of invented confidence.** Do not use an LLM's self-reported 0.85 confidence as safety evidence. Populated model fields require verbatim source quotes. Weight and portion proposals must also agree with deterministic supported-unit normalization; counts never imply weight and boxes never imply meal counts. Missing/uncertain details require donor correction. Every donor confirms all required safety fields regardless of provider. Metrics count missing/uncertain/source-mismatch fields rather than presenting uncalibrated confidence distributions. A calibrated confidence model would need separate evaluation before adoption.
4. **Canonical units and storage.** Keep kilograms for capacity comparisons, optional meal/serving counts, timezone-aware deadlines, and storage requirements. Add optional `packaging_type` (`boxed`, `sealed`, `bulk`, `other`) across proposals, confirmation, JSONB persistence, generated contracts and UI. No packaging is inferred when the source is ambiguous. Existing records without this optional field remain readable; pre-packaging idempotency receipts still replay when packaging is absent/null, while adding a new packaging value under an existing key conflicts; no second migration history or schema is introduced. Meals/servings/boxes alone do not establish weight.
5. **Versioned policy, with a safety floor.** `config/intake.json` now uses `eligibility-v2`: critical <=2 hours; high >2 through 6 hours; normal >6 hours; the exact deadline is expired. Score is clamped to [0,1] using the configured horizon and `min(pickup_end, safe_use_by)`. Description limit defaults to 2,000, with a schema ceiling of 4,000 for compatibility. Accepted input units and required review fields are configured there. Extra required fields can be added; core safety fields cannot be removed. All confirmed listings require an explicit safe-use deadline, a stricter baseline than category-dependent optional expiry. Restart API/workers together after changing policy and increment its version. Old stored responses remain audit records; new evaluations apply current policy.
6. **One AI configuration.** All adapters use `Settings.ai_*` through `integrations.ai.generate_structured`. Timeout/network failures and HTTP 5xx get one retry using the same provider, key, model and payload. Authentication/rate-limit errors, refusal, blocked/truncated output and invalid schema do not trigger another provider. Timeouts are per attempt; two attempts may consume up to twice the configured network timeout (which is not an end-to-end latency guarantee). A completed draft replay returns the saved proposal without another model call. Concurrent initial draft calls can still overlap model work; only one logical draft/donation/result is persisted. No exactly-once provider-call claim is made.
7. **Outbox effects remain at least once.** Keep `donation.submitted.v1`, `intake.evaluation_requested.v1` and `intake.evaluated.v1`. They reference persisted records using IDs/version metadata, never raw descriptions or complete handoff objects. `IntakeService.get_handoff(evaluation_id)` is the typed internal consumer port: it returns the confirmed donation and currently revalidated eligible candidate snapshots, rejects stale donation/policy/terminal state, and rechecks deadlines and route freshness. An empty candidate set is valid; it is not a fabricated match. The consumer must still fetch live recipient/driver state and recheck versions/capacity in its own transaction. No ranking or reservation occurs in intake.

## Nonfunctional requirements

- **NFR-01 safety:** deterministic confirmation/eligibility checks remain independent of providers and cannot be overridden by model output.
- **NFR-02 traceability:** stored extraction provenance and request ID, donation history/outbox correlation, persisted rule results and policy version; allowlisted JSON diagnostics for intake, extraction, validation, persistence and publication failure. Validation results are durable; counters/logs are operational diagnostics, not transaction receipts. HTTP-invalid requests have sanitized diagnostics, not full raw rejected-body persistence.
- **NFR-03 latency:** `scripts/benchmark_intake.py` measures HTTP confirmation (authentication, validation and DB commit) using local synthetic data. A 20-sample Docker/PostgreSQL run measured p50 5.50 ms, p95 9.01 ms, maximum 10.64 ms. This supports the local confirmation target only: it excludes model calls, queue waiting, concurrent load and production network conditions. It is not a production SLA or evidence of a <=2-second extraction round trip.
- **NFR-04 reliability:** real PostgreSQL tests prove same-key concurrency, rollback/retry and duplicate delivery. Broker tests cover three failed attempts and a send-before-ack crash window. Delivery may duplicate; business effects do not.
- **NFR-05 privacy:** logger accepts only application metadata; metrics use bounded status/outcome/stage labels. Tests inject contact information, donor notes and API keys and verify absence from logs/metrics. Source text still persists for the authenticated donor's audit requirement.
- **NFR-06 configuration:** urgency, text length, accepted input units and required review fields are versioned configuration. Protocol/schema bounds and mandatory safety minima remain code-level guards; configuration cannot turn them off. Policy changes need all processes restarted together.

## Observability operations

`foodbridge.observability` provides `intake_requests_total`, `eligibility_decisions_total`, `validation_latency_seconds`, `duplicate_idempotency_total`, `eligible_event_retry_total`, `intake_model_calls_total` and `intake_review_fields_total`. Histogram units are seconds rather than the PDF's millisecond metric name. Decision/publication diagnostics include persisted identifiers; metric labels never include them. Metrics are observational and can reset or be lost on process crash; they are not exactly-once accounting.

Set `FOODBRIDGE_ENABLE_INTAKE_METRICS=true` locally to expose API-process metrics at `/api/v1/metrics`. It is disabled by default and rejected outside the local environment. Each API/Celery process owns its own registry; the API endpoint does not aggregate separate worker registries. Worker JSON logs provide publication/evaluation diagnostics. Protected multi-process collection and deployment-wide dashboards remain infrastructure work; this change does not pretend to supply that deployment.

## Acceptance evidence and remaining integration

- **UT-01–UT-10, UT-13–UT-16:** extraction, schema, safety, configured review requirements, missing/invalid units, coordinates, expired/reversed windows, capacity/diet/hours and exact urgency boundaries are covered by unit/HTTP tests. Unknown fields remain donor-review issues rather than guessed values; established project error codes replace the PDF's illustrative uppercase names.
- **UT-11 / FT-05:** same-key concurrent submission returns one saved result; another command key cannot confirm a draft twice.
- **UT-12:** all four provider protocols have bounded transient retry and visible fallback tests; no real credentials were used.
- **FT-01 / FT-02 / FT-06:** authenticated HTTP persistence, source/allergen/packaging preservation, confirmation rejection, audit/outbox and duplicate guards covered. `submitted` plus separate eligible evaluation replaces a literal `ELIGIBLE` aggregate/event.
- **FT-03 / FT-04:** real DB with injected broker failure and send-before-ack crash simulation verifies pending work survives, retries reuse its ID and repeated worker delivery has one result event. This is failure injection, not a claim of a production kill-test campaign.
- **FT-07:** intake evaluation and internal handoff are covered, including excluded candidates, stale routes, elapsed deadlines and changed policy. The complete queue-driven Orchestrator -> Intake -> Matching chain is **not yet implemented or accepted**.

Tej still owns submission/result outbox consumption, general orchestration/recovery and downstream dispatch. Rushitha owns live recipient/route repositories and matching consumers. Mithil owns broader role/auth UI integration; the donor packaging/policy UI is integrated here. All consumers must use the generated contracts and shared eligibility policy. Reservation/pickup remain their existing workstreams.
